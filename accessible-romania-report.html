Executive Summary

Overall, the audited website partially supports WCAG 2.2 level AA, having 15 failures out of 55. The most critical issues are marked as such in the Observations section for each success criterion.

Remediation

WordPress seems to be used for making and maintaining this website, thus remediations should be made by someone with WordPress and coding knowledge. Some of the fixes suggested in this audit imply direct changes to the code.

Accessibility overlay

An accessibility overlay was found on each page of the website. This tool doesn't provide full compliance with accessibility standards and laws and can impact the overall accessibly in a negative way.

Good accessibility features must be offered to all users, by default, not conditionally through 3rd party tools such as overlays.

Upon a quick look, this overlay introduces the following issues:

  • It introduces many tab stops for keyboard users and screen reader users, without providing a way to bypass this repeated content.
  • It wrongfully uses links instead of buttons for some of its functionalities. These features are announced as links to screen reader users and can cause confusion.
  • The "Increase text" feature doesn't apply to all text in the page and the enlarged text overlaps other text, making it hard to read.
  • The Sitemap provided is only machine readable and not very human readable, since it's an XML file.

Overlays pose many issues in general:

  • Read more about accessibility overlays in English
  • Read more about accessibility overlays in Romanian

Recommendation: Remove the overlay widget.

ReadSpeaker plugin

The ReadSpeaker plugin didn't work when the website was being evaluated.

Screen reader users already use their assistive technology to hear the content, so this tool is redundant for them.

This tool might be used by multi-tasking sighted users or by users that might find it hard to concentrate on reading a lot of text.

If the plugin is fixed and there's user feedback that it's helpful, you could continue to use it. Otherwise, if it was meant for blind users or those with low vision, it could be removed, as screen readers are a better alternative.

PDF documents

A quick evaluation of the "ENAT-Good-Conduct" PDF revealed the following issues:

  • The title of the document isn't set. This differs from the name of the file or the visible title in the document. The title can be viewed/added in the Document Properties panel present in most PDF readers.
  • The language of the document isn't set. This can also be added in the Document Properties panel.
  • The reading order of the content in the PDF is wrong. Only at the very end are the filled-in words spoken. The filled-in text should be read in order.
    • Expected reading order: "Name of Organisation: Accessible Romania by Sano Touring" or "Country: Romania".
    • Current reading order: "Name of Organisation:Country:ENAT Member number: First year of registration:".

1.4 Distinguishable
Success Criterion Result Observations
1.4.1: Use of Color(opens new tab)

Result: Failed ❌

Observations:

Issue: In the FAQ page, the "Do I need a Visa?" accordion item: the link "Romanian Office for Immigration" cannot be easily distinguished from the rest of the text because the color and lightness of the link text and surrounding text is too similar. Users with limited color vision might have trouble identifying links if link color is the only indicator.

Links contained in a body of text (e.g. a paragraph) need a secondary indicator. A secondary indicator tells users that links can be clicked, otherwise some users with color perception impediments aren't aware of them. Usually, the recommended indicator is an underline decoration. For more solution ideas: Technique F73: Failure of Success Criterion 1.4.1 due to creating links that are not visually evident without color vision

Issue: In the page "Our story", links are only distinguishable from the rest of the body text through color alone. Examples: " ENAT", "Destination Everywhere" or "Accessible Travel Press". Users with limited color vision might have trouble identifying links if link color is the only indicator.

Use a secondary link indicator.

1.4.3: Contrast (Minimum)(opens new tab)

Result: Failed ❌

Observations:

Issue: In the FAQ page: The light blue text in the accordion items is hard to read due to not having enough contrast against the light grey background. The current contrast ratio is 2.19 to 1.

Use more contrasting colors in order to reach a minimum color contrast ratio of 4.5 to 1. For example, use black or dark blue text instead.

Issue: In the FAQ page: The text is hard to perceive if there's not enough color contrast between the text and the background.

  • For text with a size below 24px, the contrast needs to be at least 4.5 to 1.
  • For text sized at 24px or larger, the contrast needs to be at least 3 to 1.

When images are used as a background underneath text:

  • A dark colored text must be compared against the lightest color of the background
  • A light colored text must be compared against the darkest color of the background

Use a darker background image or add a layer of solid or semi-transparent black color to increase the contrast to 3:1.

Issue: In the "Tours" page: the buttons labelled "Read more" don't have enough contrast.

Increase the contrast to obtain a contrast of 4.5:1 or higher.

Issue: In the page Our story: there's not enough contrast between the "Our story" text and the background image (the contrast is around 1.84).

Use a darker image or add a solid or semi-transparent background to the text.

Issue: In the page "Our story", there's not enough color contrast between white body text and the orange background.

More details about color contrast when using background images: Technique F83: Failure of Success Criterion 1.4.3 and 1.4.6 due to using background images that do not provide sufficient contrast with foreground text (or images of text)

Issue: On the "Contact" page, the mail blue text "contact@accessibleromania.com" doesn't have enough color contrast against the white background. The current contrast is 3.96 to 1.

Use a darker blue color in order to reach a color contrast of at least 4.5 to 1.

2.4.4: Link Purpose (In Context)(opens new tab)

Result: Failed ❌

Observations:

Issue: In the "Tours" page, some of the links have an ambiguous purpose: the ones labelled "Read more". For sighted users, they can look at the nearby text to understand where the link goes, but for assistive technology users, these links are presented without the surrounding context.

Screen reader users might navigate a page through just a list of all the links in the page. For the best experience, the purpose of each link must be easily understood from the naming alone.

In order to make this experience more accessible you could:

  1. Use the existing descriptive link (e.g. "Wine and food tour in Romania") and remove the "Read more" link. There are technical improvements developers can use to make the target area / click area of the links bigger. The link target area can be enlarged to the size of the entire card. Example implementation for buttons and links: Breakout Buttons.
  2. Use a simpler solution to add more context to the "Read more" link. Example: "Read more about Wine and food tour in Romania". There are technical means to add this extra context only to assistive technology users, using either visually hidden text inside the link (Invisible Content Just for Screen Reader Users) or by using aria-label directly on the link element.
2.4.5: Multiple Ways(opens new tab)

Result: Passed ✅

Observations:

Good practices found:

  • Navigation between blog posts (previous post, next post)
  • Main menu navigating to most of the pages in the website, present in all the pages

Issue: There's no mechanism for users to see all the pages in the website in the same place. Some users prefer to have an overview of the entire website at glance in order to save time, others prefer sitemaps and searches.

The main menu would have been sufficient for this criterion if the blog posts were few and present in the menu as well, similar to the About us menu item.

But since there are more than 4 pages in the website and not all of them are located in the main menu, the website needs alternative navigation.

Ways to meet this criterion, add at least one extra way to navigate the website:

  • Add a sitemap: a separate page containing an overview of absolutely all the pages in the website, presented in an easy to read hierarchy. The sitemap can be placed in the footer of the website.
  • Add a search functionality.
  • Add "next page" links in every page, similar to the links already present at the end of blog posts. Imagine going through all the pages in the website in a circular manner. At the end, when reaching the last page, you link back to the first page. E.g. on the "Our story" page there could be a heading titled "Next up" and a link to the "Our team" page.

2.5.3: Label in Name(opens new tab)

Result: Passed ✅

Observations:

When this criterion is implemented properly it greatly improves the experience for sighted voice recognition users. These users depend on the visually displayed text to speak voice commands, which helps them operate websites.

Unfortunately, this criterion only applies to text and images of text. It doesn't apply to icons and images. This means some voice recognition users cannot use certain controls in a website because no text is provided to explain the name of that control.

Warning: The language switcher cannot easily be operated by speech recognition users. Intuitively, they might say "click language" or "click English" to open the language switcher menu, but this doesn't work.

Provide intuitive labels for icons and images, at least directly in the code. If a redesign is possible, consider including visible text labels alongside the flag images. A button starting with the word "Language" could be used instead.

Result: Failed ❌

Observations:

Issue: On the home page, the interactive controls used to show more testimonials are too small in size (13 x 7px). Result: Failed ❌

Observations:

Issue: The language switcher items doesn't update to reflect the current language and also doesn't specify the proper language code.

Suppose the page is now in French. The language switcher should then:

  • Either update the language used in the switcher and use the proper language code. More details and example: Alternative language links - Language of Parts (Level AA)

  <li><a href="..." lang="de">Deutsch</a></li>
  <li><a href="..." lang="it">Italiano</a></li>
  <li><a href="..." lang="fr">Français</a></li>

  <li><a href="..." lang="zh-hant">繁體中文</a></li>
</ul>
  • Or, keep the language terms in English as they are now, but add the correct language code lang="en".

Names of things (persons, locations, companies) and technical terms don't need to follow this criterion.

4 Robust

4.1 Compatible
Success Criterion Result Observations
4.1.2: Name, Role, Value(opens new tab)

Result: Failed ❌

Observations:

Issue: In the FAQ page, the accordion items don't communicate to screen reader users their role and whether the items are open or closed.

Screen reader users depend on roles in order to know how to interact with elements. Examples:

  • If an element is a button, I expect it to trigger an action on Space or Enter.
  • If an element is a link, I expect it to navigate to a section or a different page on Enter key interaction.
  • If an element is an input, I expect to be able to type in it, etc.

Provide the role (button) and the current state (aria-expanded) to screen reader users.

Warning: The role="link" on the logo link is redundant. The anchor (a) element is well supported in assistive technologies and doesn't need extra link roles.
